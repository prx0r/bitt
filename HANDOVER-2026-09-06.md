## What We're Trying To Do

Beat BitSec SN60. Find ALL high/critical vulnerabilities in 6 smart contract projects. Scoring is binary: find every single one or score 0. Target: 83.3% (15/15 projects).

## What Works (Proven)

### The Approach: Contrastive Auditing

From LogicScan paper (Feb 2026). Core idea:
1. Find `safeTransferFrom` calls in the target code
2. Check if `fromAddress` is verified (msg.sender, signature, allowance)
3. If NOT verified → CRITICAL vulnerability

**We proved this finds the ground truth on crestal-network:**
- Ground truth: "Anyone approving Blueprint V5 can drain tokens via payWithERC20"
- Our finding: "Unverified fromAddress in ERC20 transfer" — MATCH
- Time: 35 seconds
- File: `src/Payment.sol:25` — exact match

### The Working Script

`mining/sn60/candidates/contrastive-v1/hotfix_tracer.py`

What it does:
1. Reads Payment.sol + BlueprintCore.sol (44K chars total)
2. Finds all `safeTransferFrom` calls
3. Checks if `fromAddress` is verified
4. If not → reports vulnerability

**This works because it reads a SMALL amount of focused code, not the entire codebase.**

## What Doesn't Work (Yet)

### Scaling to All 6 Projects

The problem: other projects have 30-50 source files totaling 100-200K chars. The LLM can't process that much code in one call.

**Failed attempts:**
- `agent.py` — reads all code → LLM returns empty patterns
- `agent_v2.py` — same issue
- `agent_v3.py` — works on crestal (small codebase) but not larger projects
- `universal_auditor.py` — reads 60K chars → "Failed to parse transfers"
- `autonomous_contrastive.py` — finds wrong vulnerabilities (upgrade issues instead of payment bugs)

### Root Cause

The LLM has a context window limit. When we feed it 50K+ chars of code:
- It can't reliably parse all the transfer calls
- It focuses on the wrong patterns (upgrades, admin functions)
- It misses the payment-specific vulnerabilities

## The Hard Truth

**The contrastive auditor we built only finds TOKEN TRANSFER vulnerabilities (unverified fromAddress).**

But the other projects have DIFFERENT types of vulnerabilities:
- coded-estate: Rental marketplace logic (9 vulns) — reservations, bids, rentals
- liquid-ron: Staking/liquid staking logic (5 vulns) — operator fees, harvest
- cork: DeFi protocol logic (18 vulns) — flash swaps, redemptions
- iq-ai: Governance/voting logic (9 vulns) — proposals, voting power
- mantra: DEX/AMM logic (55 vulns) — pools, swaps, liquidity

Each project type needs its OWN set of reference patterns. We only have payment transfer patterns.

## What Needs To Happen

### 1. Build Reference Patterns Per Vulnerability Type

| Vulnerability Type | Reference Needed | Projects Affected |
|-------------------|------------------|-------------------|
| Unverified fromAddress | ✅ Built | crestal, liquid-ron |
| Rental marketplace logic | ❌ Need to build | coded-estate |
| Governance/voting logic | ❌ Need to build | iq-ai |
| DEX/AMM invariants | ❌ Need to build | mantra |
| Flash loan patterns | ❌ Need to build | cork |
| Staking/liquid staking | ❌ Need to build | liquid-ron |

### 2. Or: Use General Contrastive Approach

Instead of specific reference patterns, use a general approach:
1. Read the code
2. Ask: "What business logic invariants should this code enforce?"
3. Ask: "Which of these invariants are missing?"
4. Verify findings

This is what the original `autonomous_contrastive.py` tried, but it found wrong vulns because the LLM context was too large.

### 3. The Real Bottleneck

The LLM can handle ~50K chars reliably. Larger codebases need to be:
- Split into logical chunks (by contract/module)
- Analyzed separately
- Results merged

For coded-estate at 70K, we need to split into:
- execute.rs (main logic)
- query.rs (read-only functions)
- state.rs (data structures)
- Analyze each separately
